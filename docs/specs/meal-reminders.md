# Food reminders at the person's meal times (food goals design, part 4)

- source: founder 2026-11-17 21:13 EST (when "Seus números reais" starts, ask how many / which meals the person eats; a food reminder per meal; an athlete eating every 3 hours gets more of them) and 2026-11-18 20:40 EST ("Pode construir o resto": parts 2, 3 and 4 of the food goals design).
- picture: docs/design/food-goals-progress.html part 4 "Lembretes no ritmo das refeições" (a: the question; b: when each one comes; c: the reminders).
- checklist-signed: founder 2026-11-18 20:40 EST ("Pode construir o resto").
- decided by logic:
  - "skipped if something was logged since the previous meal" is measured from HALFWAY between the previous meal and this one (the first meal's previous is the night before's last): a breakfast logged at 08:45, after its own 08:30 reminder, must not silence lunch; only entries dated that day and typed that day count (a catch-up for yesterday never does).
  - a meal at 23:00 or later fires at 23:59 the same day, so the reminder belongs to that day's food log.
  - "Not now" (and closing the sheet) writes nothing: the single 20:00 question stays, and the sheet asks again at the next Reality check start ("Quem não responder à pergunta continua com o das 20:00").
  - "Skip this meal" only dismisses that reminder: nothing is written, the app is not opened.
  - the text shows protein and calories (the design's first example) for every meal; "of <plan>" uses the plan the Progress plan card shows (calories for the chosen goal, protein rounded to 5 g); without a plan the totals alone; with nothing logged that day no numbers line (zeros say nothing). A meal without a name ("snack", every 3 hours, an added meal) reads "Meal at 16:00".
  - "O resumo das 16:00 sai" (picture, part 4): the app has no 16:00 summary today (lib/notifications.js schedules only the 20:00 food question), so there is nothing to remove.
  - the choice lives in the account (user_metadata.food_meals, one top-level key, written whole): a preference like the food_reminders switch beside it, read by the Android server sender; durable across updates, re-installs and sign-ins; never AsyncStorage alone. Writes go through supabase.auth.updateUser({ data: { food_meals } }), which merges top-level keys (no other key touched).
  - iPhone budget (64 pending): a meal reminder other than the day's last is scheduled only inside the next 24 hours; the day's last keeps the 7-day window. Food then holds at most 7 + (meals − 1) pending (three meals: 9; five: 11; every 3 hours: 12; "Choose the times" capped at 8 meals: 14), against 7 before. The reserve used when the real counts are unknown (IOS_OTHER_RESERVED) goes from 20 to 27 (7 summaries + check-in + weigh-in + 14 food + 4 snoozes); worst-case dose total 64 − 27 − 8 expiry = 29 (was 36); with the real counts and three meals 64 − 22 − 8 = 34. Android (no such cap) schedules every meal of the 7-day window.
  - honest limit: a notification scheduled on the phone cannot read the food log when it fires. Its numbers are those the phone held when it last planned — and it plans again after every food write in the chat (refresh → syncAllNotifications), on every app open and in the background refresh; logging happens only in the app on this phone (one device at a time, AD-77), so the text is exact unless the AI estimate of a just-typed meal was still pending (counted as 0 until it arrives) or the app was never opened that day (then nothing was logged that day and the text has no numbers).
  - the Android server sender (supabase/functions/send-reminders, not active: SERVER_PUSH_ACTIVE is false in lib/notifications.js) reads food_logs with the service key, so it computes the day's totals at SEND time; it has no plan engine, so its text carries the totals without "of <plan>". It reads the entry's cloud created_at, which is the upload time (usually seconds after the log).
- daily totals vs plan: the meal reminders read the plan through lib/progressTile (one new field, planProteinG) in a small helper, foodPlanTargets in lib/notifications.js. The parallel plan-vs-actual work adds its own daily-totals-vs-plan lib; the main session can move foodPlanTargets onto it at merge.
- hard line: numbers only — what the user logged and the plan already shown on Progress. Never "eat more", never a food suggestion, never "good" / "behind".
- committed-to: next delivery (JS only on the app side; the server sender change waits for the founder's go to deploy).
