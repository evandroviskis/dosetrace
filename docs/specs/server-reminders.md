# Server-sent iPhone reminders — AD-87 B (DV-097, DV-145, A-62)

- source: founder 2026-10-15, Q10 / OPEN-06 = "A now, B next" ("siga as recomendações"): B, server-sent iPhone reminders, is its own project in 1.3.1 (docs/decisions.md 2026-10-15; OPEN-DECISIONS AD-87). The principle it must meet (docs/decisions.md 2026-10-07): "É obrigação do aplicativo que avise até a pessoa entrar no aplicativo e deletar esse protocolo" — a person still taking something keeps getting its reminders for as long as it lasts, app opened or not.
- purpose: iPhone schedules reminders on the phone only, for a short window (doses up to 10 days, fewer with many protocols because of Apple's 64-notification cap — lib/notificationPlan.js doseBudget; morning summary and the 8 PM food question 7 days). An iPhone user who does not open the app stops getting reminders when that window runs out. iOS has no reliable background run (BR-11, option C rejected), so the only way to keep them coming is for the server to send them after the phone's window ends.
- design in one line: the phone keeps scheduling its own window exactly as today and tells the server how far it planned ("planned until"); the server sends only what falls AFTER that point, with the same text, buttons and rules the phone would have used. The server path only adds; it never removes a local reminder.
- related: docs/specs/reminders-guaranteed.md (RG-6, the Android wake-up `wake-refresh`, live), docs/specs/background-refresh.md (BR-1..BR-12), docs/specs/exact-alarms.md, docs/specs/food-log.md (FL-18, FL-41, FL-42), docs/specs/one-active-device.md (A-119, same release), docs/review/features.md A-62, docs/product/DIVERGENCES.md DV-097 / DV-145.
- decisions applied (ledger, not re-asked): Silent mode cancels everything (A-108, decisions.md 2026-10-07); switched-off reminders stay off (A-109); "Show names in notifications", default on, no name on the lock screen when off (decisions.md:311); Mark complete + snooze on notifications (decisions.md:162), injectables open the app on Taken (S-25); repeats +5 / +10 when persistent reminders are on (DL-48); the 8 PM food question while a check is open, unless the day is closed, no backoff, no day-21 cut-off (FL-18, FL-42), none for a locked user, none after the last open day (FL-41, A-62); a slot is "pending" until slot + 12 h (A-40); reminders renew until the protocol is ended or deleted, a fixed course ends with its total (BR-12, council 3 #7); a network failure never cancels anything (decisions.md 2026-10-07); send-reminders stays off until A-62 is met (AD-37); no permission request at app open (AD-88); one active device per account (A-119, AD-77).
- decided by logic here (founder may override; each goes into docs/decisions.md when signed):
  1. Hand-over, not take-over: the phone keeps its local window; the server covers only after it. Reason: a phone that is offline or a server that is down must still remind (never a gap); and nothing is sent twice.
  2. iPhone only. Android keeps the A-107 / A-110 design (local + background refresh + daily silent wake-up). Reason: Android is already covered without content leaving the phone; server reminders there would double-fire.
  3. The server sends dose reminders (with repeats), the 07:00 morning summary and the 20:00 food question — the three kinds that run out with the window. Vial-expiry alerts, the Sunday check-in and the day-21 weigh-in are scheduled on their own date (or repeat) and do not run out; the low-supply alert needs a logged dose, which needs the app.
  4. Expo push (the service the app already uses for its tokens and for wake-refresh, already named in the privacy policy as the push service), not a direct Apple (APNs) connection. Reason: same token, no new key or vendor, free.
  5. The sender runs every minute. Reason: reminders are set to the minute and the phone delivers on the minute; "it ran every 15 min" is one of the reasons the old sender was refused (decisions.md:589).
  6. When the phone could not report (opened while offline), a duplicate is allowed rather than a gap (principle: never miss a reminder).
  7. No new screen and no new Settings switch: the existing switches apply. AD-87 A (the window's last notification "Open DoseTrace to keep getting your reminders" + the Today warning) becomes the fallback, shown only while the server is not confirmed to cover this iPhone.
- found while writing (for the coordinator): AD-87 A was decided for 1.3.0, but its text is not in the code on any branch (no "keep getting your reminders" string in i18n/translations.js; no end-of-window logic in lib/ or screens/). Under "approved → next build" it is owed in 1.3.1 with its picture (OPEN-DECISIONS "Approvals still owed" item 20). SR-17 depends on it.
- code (expected): supabase/functions/send-reminders/ (rewritten — replaces the dormant version; rebuild = replace), a generated copy of lib/notificationPlan.js rules + the needed i18n keys for the function (script + parity test), one migration (device report table, notification_sends, run claim, prefs read function, kill switch, cron); lib/notifications.js (device report, whole-slot budget, permission-free token registration, removal of the dead Android `usesServerPush` path), lib/notificationActions.js / lib/notificationPlan.js notifTapTarget (remote payload read), the AD-87 A fallback (TodayScreen + the last local notification), i18n only if AD-87 A's strings are added there.

## Technical design

### Data (one migration, applied only on the founder's "pode aplicar")

| Object | Columns / body | Access |
|---|---|---|
| `reminder_device_plans` (new) | `expo_token` (pk, references `push_tokens(expo_token)` on delete cascade), `user_id` (→ auth.users cascade), `device_id` (A-119), `reported_at`, `timezone`, `language`, `app_version`, `permission`, `dose_until jsonb` ({protocol id: moment}), `summary_until`, `food_until`, `accepted_at` | RLS: insert / update / delete own row (`auth.uid() = user_id`); read own; service role reads all |
| `notification_sends` (new on production — exists only in repo SQL, DR-3) | `dedupe_key` (pk: token hash + kind + protocol id + local day + slot + repeat), `user_id`, `kind`, `slot_at`, `sent_at`, `ticket_id` | RLS on, no policy (service role only); rows older than 4 days pruned each run |
| `send_reminder_runs` + `claim_send_reminders()` | like `claim_wake_refresh()`: advisory lock, at most one run per 50 s, 1-day history | service role only |
| `reminder_prefs(uuid[])` | security-definer read of `silent_mode`, `dose_reminders`, `food_reminders`, `persistent_reminders`, `notif_show_names` from the account metadata (replaces one admin API call per user) | service role only |
| `app_flags` row `send_reminders` | `enabled` (kill switch), `dry_run` | service role only |
| cron `dosetrace-send-reminders` | `* * * * *`, pg_net POST to the function (verify_jwt off, protected by the claim — same pattern as wake-refresh, no secret needed) | — |

### Sender, each minute
1. Claim the run; stop if the switch is off.
2. Read iOS devices with a plan report, on the account's active device (A-119), permission granted, whose earliest "planned until" has passed. Usually zero rows → done.
3. For those accounts only: active protocols (not deleted, not purged), Taken / Skipped dose logs of the last 36 h, prefs, open reality check, closed food days and the free-days anchor; RevenueCat only for accounts that would get a food question.
4. Plan with the generated copy of `lib/notificationPlan.js` (dueDateKeys, reminderTimes, handledSlotIndexes, morningSummaryPlan, foodNudgeDays, remindersForAccess) and the moment rule of the phone (SR-12). Keep items whose moment is after "planned until" and inside the retry window.
5. Claim each item in `notification_sends`, send through Expo in batches of 100 (`title`, `body`, `data`, `categoryId` = the phone's category, `sound`, `priority: high`, `ttl` per SR-14). Release claims Expo did not accept; read receipts of earlier sends; delete dead tokens.
6. Return counts only.

### Expo push vs Apple direct
Expo (decided by logic 4). Its push service needs the app's Apple push key in EAS credentials — confirmed in use already: 8 iPhone tokens on 7 accounts are registered on production today (read-only count, 2026-10-20). Direct APNs would need a .p8 key in function secrets and HTTP/2 signing, for no user benefit at this size.

### Client changes
- `lib/notifications.js`: build and send the plan report at the end of every full resync and after a standalone protocol schedule (debounced; offline → retried at the next resync); budget whole slots on iPhone; `registerPushToken` reads the permission instead of requesting it (AD-88); remove `SERVER_PUSH_ACTIVE`, `usesServerPush` and the Android branches that cancel local reminders.
- `lib/notificationActions.js` / `lib/notificationPlan.js notifTapTarget`: read the data of a remote notification as reliably as a local one (iOS may place it differently); the snoozed copy uses the local id carried in the data.
- AD-87 A fallback (SR-17): the end-of-window text and Today warning read "server covers this iPhone" from the last accepted report.
- Generated server copy: a script writes the plan rules and the needed i18n keys into the function folder; a test fails when the copy is out of date.

### Rollout
Migration and deploy on the founder's go → dry run (SR-23) → switch on → device proof (SR-24). Off again with one row; phones keep their local reminders either way. Before building: journey-review on this flow (CLAUDE.md, substantive flow change); dt-council and ship-check before the build.

## Questions for the founder

1. **Should server-sent reminders show compound names?** When the app has not been opened for a while, the server writes the reminder text and it travels through Expo and Apple to the phone (the phone's own reminders never leave the phone). Names are already stored on our server with the protocols; what is new is the text passing through the push service.
   - A — Same as the phone: the name shows when "Show names in notifications" is on, never when it is off (SR-8 as written). The privacy policy's push-service line says so.
   - B — Server-sent reminders never carry a name or dose ("Dose reminder" / "2 scheduled today."), whatever the switch says. More private; the person sees a plainer reminder once the app has gone unopened for ~10 days, without knowing why.
   - C — The text is completed on the phone (an iPhone notification extension fills in the name from the phone's own data). Most private and looks the same, but it adds native iPhone work and risk inside a ~3-day release.
   - **Recommendation: A.** It keeps one rule the person already controls, and the extra exposure is the encrypted transit through a push service we already list. Note: the standing GDPR Art. 9 flag (build 49) says a lawyer should look at health data handling; this adds one more processor use to that review. If you want zero names outside the phone, choose B now and C later.
