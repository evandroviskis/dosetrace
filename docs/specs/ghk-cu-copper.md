# Copper this cycle (GHK-Cu, GLOW, KLOW)

- source: founder 2026-11-11 00:37 EST ("Ok para as duas ideias", P11 (a): cobre acumulado por ciclo do GHK-Cu, só conta, sem dizer se é muito ou pouco); picture docs/design/ghk-cu-cobre-ciclo.html (commit 661070b8) approved 2026-11-24 13:19 EST ("Em relação ao GHK, eu concordo com suas recomendações"; Second Brain dosetrace/02-decisoes.md). The picture is the spec: texts, rows, sheets, factors and sources as drawn.
- decided in the picture (not asked again): the form on the label is optional and starts at "Não sei" (range lowest–highest form); GLOW and KLOW count only when the person says how much GHK-Cu the vial has (never a recipe default, lib/compounds BLEND_RATIOS is NOT used here); only Taken doses of the current run, each with its own recorded amount; the two values live on the protocol and apply to the whole cycle (no per-dose storage).
- decided by logic (CLAUDE.md "decide what is already decided", one line each):
  - A run is one protocol row: "Retomar" already creates a new row (lib/protocolEnd restartAsNew), so the cycle is the Taken rows of this row from the start date's local day; "Continuar" (still_going_at / Ciclo concluído) keeps the row, so it keeps the cycle.
  - A Taken row without its stamp (older rows) counts at the protocol's dose in force at that moment (lib/doseStamp stampForTaken), the same rule the curve uses; a row whose unit is not a mass (IU, ml) cannot be converted and is not summed; on a protocol whose own dose unit is not a mass the section is not shown.
  - The ended run's page (Encerrados) shows the same section titled "Cobre no ciclo" (picture box 2); its two rows stay tappable there — they describe the vial's label, not the protocol's schedule, and a read-only blend row would be a dead end.
  - A GHK-Cu amount above the vial total (the vial total edited lower later) counts as not given: the ask comes back, nothing is clamped or invented.
  - The Fold's Today right page draws the same ProtocolDetail, so it shows the same section (design consistency, founder 2026-11-20).
- sync: two new protocols columns, `copper_form` (text: complex · acetate · bis; NULL = Não sei) and `ghk_cu_mg` (numeric, blends only; NULL = Não sei). Regular columns added after the cloud schema (lib/syncMappers CLEARABLE_COLUMNS, the A-121 `ends_on` rule): always sent, NULL included, so a choice taken back to "Não sei" reaches the cloud; a pulled NULL is written; a cloud without the column (key absent) or a value still waiting to go up leaves the phone's value. Until the migration is applied the cloud answers PGRST204: the write is retried without the column, a value is kept on the phone (optional_pending) and sent once the cloud accepts it. Migration supabase/migrations/20261124000000_protocol_copper.sql, additive, NOT applied (asks the founder's "pode").
