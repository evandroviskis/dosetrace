# Profile in a synced table (account_profile)

- source: founder 2026-11-24 13:13 EST (Second Brain dosetrace/02-decisoes.md): "pode corrigir. Faz o desenho... os testes próprios e vamos fazer tudo junto... não tem por que deixar para depois" — move the profile out of user_metadata into a synced table, in the same package (branch feat/profile-synced): table with RLS + a migration that copies every current profile (written only; applying it needs his "pode aplicar"), the app reads the table and falls back to user_metadata when something is missing, every write also mirrors to user_metadata while 1.3.0 / 1.3.1 are in the stores; picture docs/design/perfil-sincronizado.html.
- why: CLAUDE.md "NEVER lose user-entered data" — user data belongs in the SQLite <-> Supabase synced tables, not solely in Supabase user_metadata (no history, no tombstones, overwrite-prone). Found 2026-11-24 while drawing the adherence report (report_name, docs/design/relatorio-adesao.html).
- decided by logic (each in one line):
  - table name public.account_profile, never public.profiles: that one is the legacy table (id, email, name, plan) the core tables reference by foreign key (scripts/load-test/prod-schema.sql) and delete-user removes by id;
  - one row per account with ONE jsonb payload merged per key, not one column per key: the sync engine already does exactly this for calc_inputs (DV-010: push = the cloud payload as read now + the keys changed here, only over the updated_at it read); per-column rows would be replaced whole (last writer wins) between the app and the server copy; a new key (report_name, the onboarding answers of later releases) needs no migration; the payload has user_metadata's own shape, so the copy and the mirror are 1:1;
  - which keys: every user_metadata key except the sign-in provider's identity claims (Apple / Google rewrite them at each sign-in), the values that already have their own synced table (calc_inputs, reality check, weigh-ins, lab stars and labels: user_metadata only mirrors them) and the migration markers — one list in the app (lib/profileStore EXCLUDED_KEYS) and in the SQL (dt_profile_keys);
  - mirror first: a profile write goes to user_metadata first (merge, only the keys sent) and to the table only after the auth server accepted it. So user_metadata stays complete for 1.3.0 / 1.3.1, send-reminders, version-notice and the admin panel, and a refused save (offline, A-119 not the active phone) is refused exactly as today — no screen changes;
  - the old versions' own writes reach the table through a trigger on auth.users (only the keys that changed, merged over the row; an error is a warning, never a failed sign-in);
  - reads (founder B1, 2026-11-24): while user_metadata is written first, user_metadata wins and the table only fills keys it lacks; at the cutover the table wins once read in full on the phone;
  - one device at a time (A-119 / AD-77): nothing here is about two phones writing at once; the per-key merge protects against the server copy and the old versions' writes.
- not visual: no screen, text or notice changes (no new string); the person sees exactly the same profile before, during and after the move. The picture says so explicitly. One exception, PS-18 below: the line after an Edit profile save kept on the phone without internet (the app's existing toast, as DV-114's gate answer).
- offline Edit profile (founder 2026-11-24, admin panel: "Editar o perfil (nome, data de nascimento etc.) sem internet deve continuar recusado, como hoje?" → "B) Guardar no celular e enviar quando a internet voltar"), PS-18..PS-23:
  - where it waits: account_profile.pending_meta (local column) — the keys and values of an Edit profile save user_metadata has not accepted yet; durable SQLite, numbered by the A-119 change sequence, wiped only by the intended sign-out (after the unsent warning);
  - precedence (per key, no clock): a key in pending_meta wins over user_metadata and over the table's payload, in the mirror period and after the cutover, until user_metadata accepts that same value; then it leaves pending_meta and the normal rules (B1) apply again. No updated_at comparison: user_metadata has no per-key time, and the phone clock can be moved;
  - order (mirror first, unchanged): the waiting edit goes to user_metadata as ONE merge write of only its keys (through the one updateUser wrapper: the A-119 guard, then user_metadata, then the table step); the cloud table row waits while pending_meta has keys, so it is never ahead of user_metadata;
  - when: app start and sign-in (after the account guard), connection back, a completed sync pass, app back to the front, the deliberate sign-out's send-first step; never inside onAuthStateChange; one send at a time (Edit profile's save and the flush in one queue);
  - a refusal that is not a connection problem (A-119 DT001, a 4xx) is refused exactly as before (Edit profile stays open, the error sheet); 429 / 5xx / no internet keep it (the DV-114 rule, lib/pendingGate isRetryableError);
  - at the cutover (MIRROR_PERIOD false, the mirror removed) an Edit profile save becomes a table patch like any other write and pending_meta / the flush go away in the same change.
- code: lib/profileStore.js (rules), lib/profile.js (app wiring), lib/profileWrite.js (the step after a metadata write), lib/profileName.js (getNickname, getReportName, saveReportName), lib/supabase.js (the updateUser wrapper; getCachedUser / peekCachedUser / readStoredUser), App.js (the gates; the copy after the account guard), lib/syncCore.js (TABLES, LATE_TABLES, FULL_PULL, push / pull / import), lib/syncMappers.js, lib/sync.js, lib/schema.js, lib/changeSeq.js, lib/database.js (sign-out wipe, local owner), lib/unsentSummary.js, supabase/functions/delete-user/index.ts (list only; it tolerates a missing table), supabase/migrations/20261124000100_account_profile.sql (NOT applied).
