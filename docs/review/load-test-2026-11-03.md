# Load test of the sync path, 2026-11-03

Goal (founder, 2026-11-03): simulate 100 and then 1,000 people using the app at the same time, find
where it chokes, fix it, measure again. Production was never load-tested and nothing was applied to
it. Everything ran locally on Docker.

## Rig

- **Schema:** `scripts/load-test/prod-schema.sql` is a copy of production's public schema. It was read on
  2026-11-03 with read-only catalog queries (columns, keys, foreign keys, every index, every RLS policy
  verbatim, the triggers, `dt_pre_request` / `dt_require_active_device` / `dt_device_guard` /
  `device_status`, grants, role settings). No user row was read. `auth.uid()` and `auth.role()` have
  exactly production's definition. Left out: the admin functions, cron jobs and the device RPCs
  other than `device_status`.
- **Images:** `supabase/postgres:15.8.1.085` and `postgrest/postgrest:v12.2.12`. Both were already on
  the machine, so nothing was pulled. Production runs Postgres **17.6**.
- **Compute:** sized like production's Micro instance. Postgres settings are production's
  (shared_buffers 224MB, work_mem 2184kB, effective_cache_size 384MB, 60 connections,
  random_page_cost 1.1, jit off). The container has 1 GB of memory. Postgres **and PostgREST share the
  same 2 cores** (Supabase runs both on the project's instance). The PostgREST pool is 10. Role
  settings match production: statement_timeout 8 s (authenticated) / 3 s (anon), lock_timeout 8 s,
  safeupdate, and `pgrst.db_pre_request = public.dt_pre_request`.
- **Data** (`scripts/load-test/seed.sql`), about one year of use at 5,000 accounts, 1.56 GB:
  - dose_logs: 5,474,930 (3 protocols × 365 days per user)
  - food_logs: 910,000
  - calc_snapshots: 455,000
  - analytics_events: 205,000
  - biomarkers: 200,000
  - reality_checks: 60,000
  - lab_prefs: 50,000
  - vials: 30,000
  - protocols, reminders, vaccines: 15,000 each
  - one row per user in each of the rest
- **Virtual user** (`scripts/load-test/run.cjs`): each has its own HS256 JWT. Each sends the app's
  headers (Authorization, `x-dt-device` of its active device, `x-dt-app-version`). Each replays the
  app's sync pass in a loop, sequentially as the app does it, with a random 0–1 s pause between
  passes. One pass is 16 requests:
  1. `POST /rpc/device_status` (deviceFlow.gate, every pass)
  2. 12 × `GET /<table>?select=*&user_id=eq.U&updated_at=gt.W&order=updated_at.asc,id.asc&limit=500`.
     This is pullChanges / lib/syncPager, with a watermark 2 days back.
  3. `GET /protocols?select=id&user_id=eq.U&purged_at=is.null&order=id.asc&limit=1000` (selfHealProtocols)
  4. Push: `POST /dose_logs?select=id,updated_at` (single object, return=representation) and
     `PATCH /vials?id=eq.V&select=id,updated_at`
- **Measurement:** 5 s warm-up, then a 30 s measured window. All virtual users start within 0.2 s, like
  a stampede after a push notification.

Run it with `node scripts/load-test/run.cjs`. It is opt-in and never part of `npm test`; it takes
about 4 minutes. Results go to `$TMPDIR/dt-load-test-*/result.json` (env knobs are in the script
header).

## Before / after

Same rig, same data, same run. "After" means with
`supabase/migrations/20261103120000_perf_indexes_rls.sql` applied.

| | 100 users before | 100 users after | 1,000 users before | 1,000 users after |
|---|---|---|---|---|
| requests / s | 104 | **2,771** | 119 | **2,370** |
| p50 | 399 ms | **2.8 ms** | 10,001 ms | **349 ms** |
| p95 | 3,293 ms | **15.7 ms** | 10,008 ms | **724 ms** |
| p99 | 5,573 ms | **30.6 ms** | 10,021 ms | **1,638 ms** |
| errors | 0 | 0 | **2,399 of 3,565 (67%)**, all PGRST003 | **0** |
| full sync passes completed (30 s) | 167 | 5,190 | **0** | 4,667 |
| sync pass p50 / p95 | 11.2 s / 18.8 s | 48 ms / 225 ms | none finished | 5.9 s / 7.6 s |
| Postgres CPU (of 200%) | 173% (max 198) | 68% | 162% (max 197) | 63% |
| PostgREST CPU | 12% | 73% | 21% | 80% |

PGRST003 means PostgREST waited 10 s for a free database connection and gave up. In the app this is
a failed sync.

**Indexes vs RLS rewrite.** A separate run applied only the 9 indexes, without the policy rewrite. It
gave 2,425 req/s with p95 32 ms at 100 users, and 2,840 req/s with p95 403 ms at 1,000. That is the
same as the full migration, within run-to-run noise. **The indexes are the fix.** The
`(select auth.uid())` rewrite made no measurable difference to this workload. The reason: every app
query already filters `user_id = U`, so the per-row `auth.uid()` only runs on the handful of rows
returned. The rewrite still clears the advisor's 56 `auth_rls_initplan` lints. It helps a read that
returns many rows (a full-import page is 500 rows), and it costs nothing.

## What choked

`EXPLAIN (ANALYZE, BUFFERS)` was run as the `authenticated` role, with the user's claims and the
device headers (5,000 users, 5.5 M dose logs):

| query | before | after |
|---|---|---|
| pull dose_logs (since the watermark) | **222 ms**, Seq Scan, 99,429 pages read, 5,474,994 rows thrown away | **0.1 ms**, Index Scan dose_logs_user_updated_idx, 10 pages |
| full-import page of dose_logs (first login) | **231 ms**, Seq Scan | **0.3 ms**, Index Scan |
| pull protocols / self-heal ids | 1.2–1.3 ms, Seq Scan of every protocol | 0.0–0.1 ms, Index Scan |
| pull vials | 1.7 ms, Seq Scan | 0.1 ms |
| pull biomarkers | 9.5 ms, Seq Scan, 199,990 rows thrown away | 0.1 ms |
| pull food_logs / vaccines / reality_checks / calc_snapshots | 0–0.6 ms, already indexed | same |
| insert a dose log (all triggers) | 1.7 ms | 1.2 ms |
| pre-request guard (`dt_pre_request`, write) | 1.6 ms | 1.1 ms |
| purge a protocol (trigger deletes its dose logs and vials) | **185 ms** (protocols_purge_children scans dose_logs) | **1.5 ms** |
| delete an account (auth.users cascade) | **707 ms** (dose_logs FK cascades: 510 ms + 174 ms) | **8.6 ms** |

1. **dose_logs had no index except its primary key.** Every sync pass of every user read the whole
   table. At 100 users, two cores were spent on sequential scans of 5.5 M rows (Postgres 173–198% CPU),
   and a sync pass took 11–19 s. At 1,000 users, the 10 pool connections were always busy with those
   scans. Everything else (even `device_status` and the indexed tables) queued behind them for more
   than 10 s. **Not one sync pass finished.**
2. protocols, vials and biomarkers had the same problem at a smaller size. reminders and
   admin_devices had unindexed foreign keys (the advisor's list of 9).
3. The unindexed `protocol_id` / `user_id` foreign keys made **purging a protocol** (185 ms) and
   **deleting an account** (707 ms) scan dose_logs. Both run inside a transaction that holds locks.
4. **The per-request device guard is fine.** `dt_pre_request` → `dt_require_active_device` reads
   `device_policy` (one row), then `account_devices` by its primary key. `device_status` reads
   `auth.users`, `account_devices` and `user_devices` by primary key. All of this was already
   indexed and costs about 1 ms. The migration does not touch it.
5. **After the fix, at 1,000 users, the limit is the instance's CPU, not a query.** Every query is
   under 1 ms in the database. Latency is the same for every request type (p50 about 350 ms), which
   means queueing for the shared 2 cores: PostgREST about 80–90% of a core, Postgres about 65%, plus
   the container's networking. Raising the PostgREST pool from 10 to 20 changed almost nothing
   (2,663 req/s, p95 503 ms). The load generator used 18% of one core, so it was not the limit. In
   short, the rig's Micro-sized instance serves about 2,400–2,800 requests/s. That is about 150–170
   full sync passes per second.

Two notes. They are not in this migration:

- `device_status` updates `user_devices.last_seen_at` on **every** sync pass. That is one write per
  pass per user. At 1,000 users it is among the slowest calls (p95 841 ms, with the two pushes at
  888–915 ms). Writing it at most once every few minutes would remove most of those writes. This
  changes the function's behaviour, so it is left for a decision.
- In a first rig run, PostgREST was not pinned to the database's cores and could use all 15. It
  burned 700–1,200% CPU for less throughput (1,850 req/s at 1,000 users). That is the Haskell runtime
  spreading over many cores; it does not apply to Supabase, where PostgREST runs on the instance.

## What changed: `supabase/migrations/20261103120000_perf_indexes_rls.sql`

1. **Nine indexes**, all plain `create index if not exists`:
   - `dose_logs (user_id, updated_at, id)` and `dose_logs (protocol_id)`
   - `protocols (user_id, updated_at, id)`
   - `vials (user_id, updated_at, id)` and `vials (protocol_id)`
   - `biomarkers (user_id, updated_at, id)`
   - `reminders (user_id)` and `reminders (protocol_id)`
   - `admin_devices (user_id)`

   The `(user_id, updated_at, id)` indexes match the keyset pull exactly (filter, order and cursor).
   They also cover the `user_id` foreign key. After this, no foreign key in public is left without a
   covering index (checked on the rig).
2. **56 policies rewritten** with `ALTER POLICY … USING / WITH CHECK`, so the role, command and
   permissive flag cannot change. The 56 policies span profiles, dose_logs, reminders, biomarkers,
   analytics_events, referral_codes, referrals, vaccines, food_logs, reality_checks, calc_snapshots,
   calc_targets, push_tokens, reality_check_open, calc_inputs, protocols, vials, team_messages and
   lab_prefs. Each expression is production's text with only `auth.uid()` →
   `(select auth.uid())`.
3. **referrals:** the two permissive SELECT policies (referrer, referred) are now one policy, named
   "Users can see referrals they made or received", whose rule is their OR. Postgres already ORs
   permissive policies, so the rule is the same.
4. **analytics_events keeps its two INSERT policies.** One is for `authenticated` (user_id must be
   null) and one for `public` (own id). Different roles cannot be one policy without changing who may
   insert.
5. The unused indexes stay; they are out of scope.

`supabase/migrations/20261103000000_…` is already taken by `admin_annotations` on `main`. That is why
this file uses `20261103120000`: two files with one version break `supabase db push` after the
branches meet.

## Proof the meaning did not change

- `__tests__/perfIndexesRls.test.js` checks the migration statically against
  `__tests__/fixtures/prodPolicies-2026-11-03.json` (production's pg_policies, verbatim). It has 7
  tests. It failed before the migration existed. It also catches a changed column: a mutation from
  `user_id` to `id` failed it.
- On the rig, with the real schema, the same 122 cases ran before and after the migration, and every
  result is identical (status, row count, error code). The cases are user A against user B on all 19
  tables:
  - read B's rows
  - insert as B
  - update B's rows
  - delete B's rows
  - read and update own rows
  - both halves of the referrals rule (A sees exactly the 2 referrals it is part of)
  - the vials DELETE rule (the vial of a protocol in the bin is not deletable; a live one is)
  - a withdrawn team message stays hidden
  - another device of A → DT001
  - anon reads nothing

  A never read, changed or deleted a row of B. analytics_events accepts the insert only because its
  trigger stores it with user_id null; 0 rows were stored under B.
- After the migration, the live `pg_policies` equal production's text once Postgres's
  `( SELECT auth.uid() AS uid)` is read back as `auth.uid()`. That holds for every policy (roles,
  command, permissive flag, USING, WITH CHECK). The count went from 59 to 58 (the merge), and no bare
  `auth.uid()` is left.
- `scripts/a119-pg-rehearsal.cjs` still passes 38/38. Its own fixture is a simplified schema, so the
  new migration does not apply to it; the device-guard behaviour was re-checked on the real-schema rig
  instead (DT001 before and after).

## Risk of applying (the founder decides; nothing was applied)

- **Locks:** `create index` (not concurrently) blocks writes to that one table while it builds.
  Reads continue. On production today the tables are tiny (about 800 dose logs, 75 protocols, 68
  vials, estimated), so this is milliseconds. On the rig, with 5.5 M dose logs, the whole migration
  took 3.7–5.1 s. `ALTER POLICY` takes a brief exclusive lock per table. Apply at a quiet moment; if
  pasted into the SQL editor by hand, wrap it in `begin; … commit;`.
- **Meaning:** proven equal as above. Remaining gap: the rig is Postgres 15.8, production is 17.6. The
  indexes are plain btree and the policies are simple expressions, so the same behaviour is expected,
  but it was not run on 17.
- **Writes:** a dose-log insert maintains 2 more indexes (insert p50 at 100 users after: 5.3 ms,
  including the HTTP round trip).
- **Rollback:** written in the migration header: drop the 9 indexes and re-run the original
  policies from the fixture.

## Not verified

- Production itself: no load was sent there. Real-world latency to Supabase (network) adds to every
  number above.
- Postgres 17.6 (production) vs 15.8 (rig).
- Supabase's real PostgREST pool size for this instance; 10 was used (PostgREST's default) and 20 was
  tried.
- Other traffic: GoTrue (sign-in, token refresh), Realtime, Edge Functions (AI scan, food log),
  analytics inserts and push-token registration were not in the load.
- The first-login full import was measured only by EXPLAIN (one page: 231 ms → 0.3 ms), not as load.
