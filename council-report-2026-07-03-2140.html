LLM Council · DoseTrace

Compound data foundation — build it right, or build it small?

The question: Today a protocol stores the compound's localized display name and lets users free-type it — so data is dirty (mistypes like "Blow" for the blend "Klow"; the same compound stored differently per language). How should the compound-selection foundation be built now to serve a future B2B version (trainers/doctors sourcing protocols) and near-term PDF export — without over-building or prematurely committing to a regulated model?

Agree High-confidence signals

  • Store a stable, language-independent compound_id on the protocol — not the display name. Unanimous, and the only irreversible decision. Dirty strings can't be un-mixed later.
  • Localization is a display layer over the id. "Retatrutida" is an alias, not a stored value or a 6th translation block.
  • "Select-only" vs "never block" is a false choice. Resolve it with an always-available "can't find it? add it" that mints an attributed, unverified record — never free text into the name field.
  • Alias / nickname search is the primary find path. People know the supplier nickname ("Klow"), not the canonical name — this is what actually kills the Blow-vs-Klow problem.
  • Don't over-build for B2B pre-launch. Defer component-ratio models, the server registry, provider metadata, and the exhaustive research pass.
  • The B2B / PDF-to-doctor direction needs legal review before it ships. It strains "not medical advice."

Clash Where reasonable advisors disagree

The Expansionist vs everyone else — on timing and on blend component ratios.

Four advisors + all reviewers
Minimal now. A curated database asserting gray-market blend ratios is legal exposure, not just an asset. Build the moat later, after legal clearance.
The Expansionist
The registry is the sellable asset — build component ratios + versioning now; the clean taxonomy is a real moat nobody in the space has.

Resolution: it's a sequencing call, not a true conflict. The moat is real but belongs post-legal-review. The one Expansionist idea to adopt cheaply today: capture unmatched/added entries as a roadmap signal queue.

Blind spots Only caught in peer review

  • Authorship is the real regulatory hinge. Free text is the user's claim about what they took. A canonical record with component ratios is your claim — the app now asserts "this is what KLOW contains" about unverified products across 6 jurisdictions. Framing an "added" compound as the user's own label preserves user authorship until legal review.
  • Merge/relabel silently rewrites history. Re-mapping a user's custom entry to a canonical id later changes their historical dose log — a data-integrity and evidentiary problem if it's been exported to a doctor. Needs a dedup/authority policy before dirty records pile up.
  • A doctor-facing PDF may need jurisdiction-specific disclaiming, not one global "not medical advice."
  • Offline / local-first sync of a growing registry across 700 users (a later, but real, concern).

Recommendation

Build the minimal canonical layer now; defer the asset/B2B ambitions.

  • Compound record: { id, slug, canonicalName, category, aliases[] }. A components[] field may exist but stays empty — do not publish blend ratios.
  • Store compound_id on the protocol (dual-write alongside the existing name during the pre-launch transition; trivial backfill).
  • Picker = select-first with alias search + always-available "Can't find it? Add it" that mints an attributed, unverified record framed as the user's own label.
  • Log unmatched/added entries as a roadmap queue.
  • Do not model component ratios, build the server registry, run the exhaustive research pass, or build provider/B2B features. Get legal eyes on the doctor PDF + B2B before either ships.

This refines the owner's plan: storing the id was the right instinct; the council pulls back component-lists/registry/exhaustive-research as premature and legally hot, resolves select-only with an attributed escape hatch, and flags authorship as the thing to clear legally before the pivot.

◆ The one thing to do first

Define the compound record schema and store compound_id on the protocol (dual-write). Transcribe the existing 122 compounds into a compounds.js registry with ids + aliases, add the field, switch the picker to write the id. Everything else grows around that one irreversible move.

The Contrarian — full response
Store the id, not the display name — correct and cheap. Everything else is where the flaw is. "Select-only, no free text" directly contradicts "never block a user." You can't have both. In a 700-person network, underground blends not in your list will appear weekly; a select-only picker becomes a wall, and you've guaranteed it by forbidding the escape hatch. Answer: allow a "custom compound" that writes a real record with source:user, canonical:false — dirty but attributed and mergeable later. Don't pretend you can enumerate an adversarial, ever-changing gray-market catalog. The harder question you're avoiding: the B2B/medical reframe isn't a data-model problem, it's a liability problem. The instant a provider "sources protocols and follows doses," you're no longer a personal log — you're dosing infrastructure for controlled/unapproved substances across 6 jurisdictions. A cleaner component list makes your data more useful as evidence, not less. Minimum viable, no regret: canonical id + display name + aliases. Skip component-lists, categories, server-registry scaffolding until B2B is validated and legally cleared. The regret isn't under-structuring — it's spending launch runway architecting for a pivot regulation may forbid.
The First Principles Thinker — full response
Store the id, kill the free-text field — not over-engineering; it's the only irreversible decision, because dirty free-text can't be un-mixed later. But the question smuggles a false framing. "Select-only clean data" vs "never block" isn't a real tension — "not in our list" is two problems: (1) compound exists, uncatalogued → a coverage bug on YOUR side; (2) user genuinely has something novel. Case 1 is 99% of a 700-person network sharing ~120 compounds. The answer isn't free text — it's a fast "request/add compound" path that mints a canonical record; the user picks from a growing list, you never lose the string to a display name. Sharper cut: you're building B2B regulatory infrastructure to solve a launch-week autocomplete problem. Component lists, provider metadata — answering a question no user has asked. Minimum viable: canonical record { id, canonicalName, aliases[], category }; store id on protocol (non-negotiable); localization is a display layer over the id, never stored; leave components[] nullable, populate never until a real B2B requirement defines the shape. The regret you're avoiding isn't "we didn't model components" — it's "we stored 'Retatrutida' as a string."
The Expansionist — full response
Build the canonical registry — but framing this as "clean data foundation" is thinking too small. The registry is the actual asset that makes the B2B pivot defensible. A curated, alias-mapped, multilingual, blend-decomposed compound database is itself a product; nobody in the peptide space has clean canonical data with component breakdowns (KLOW → its constituents at real ratios). Trainers/clinicians will pay for that structure. Go further: add a components model with per-component dose ratios; version the registry from day one (schema_version + per-record updated_at) so a server registry can push new compounds to 700 users without an app release; capture user free-text as signal, not dirt — route unmatched entries to an "unmapped" queue that becomes your roadmap. Resolve the tension: select-only for matched compounds, "request/add new" for the rest. The medical direction shouldn't just shape the model — the model should become the thing you sell.
The Outsider — full response
Store the ID, not the typed text — right, do it before launch. Everything else is heavier than the problem. A normal user opens the app and wants to log what they injected in under ten seconds. The scary failure isn't duplicate spelling — it's "my compound isn't listed, so the app won't let me log it, so I stop using the app." A logbook that blocks you is broken. Never make the list a wall: always offer "can't find it? add your own," store as free-text flagged "unverified," merge into a real ID later. Assumptions a stranger wouldn't make: (1) people may know only the supplier's nickname ("Klow") — search-by-nickname is the PRIMARY way people find things. (2) "Blow" vs "Klow" may be an ordering/mis-tap problem, not spelling — confirm the choice with a second detail before saving. (3) the PDF-for-a-doctor goal strains "not medical advice" — get it reviewed before it ships. Simplest non-regret: pick-from-list with nickname search, permanent IDs, always-available "add unlisted." Skip the trainer/doctor platform for now.
The Executor — full response
MVP that avoids regret: canonical-record + store-id + select-only picker. Defer the "exhaustive" ambition. The regret-proof core is stable IDs on protocols. Sequence: (1) schema { id, slug, canonicalName, category, aliases[], components[]? }; ship compounds.json with the ~122 you already have — you're transcribing existing arrays into IDs (one afternoon). (2) Add compound_id column alongside the existing name field; write both — kills migration risk. (3) Rebuild picker as select-only over the JSON, search matching canonicalName + aliases; free text goes behind a "Can't find it? Request" button that logs the string. (4) Ship; backfill compound_id on the few pre-launch rows, retire name field later. Defer: blend components, server registry, exhaustive research, full 6-language names. The real trap: translations — canonical names mostly don't need translating; treat "Retatrutida" as an alias, NOT a 6th translation block.
